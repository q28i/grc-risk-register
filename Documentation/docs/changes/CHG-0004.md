# CHG-0004: Risk Register & 3x3 Deterministic Scoring Engine

- **Change ID**: CHG-0004
- **Component**: Risk Management & Calculation Engine
- **Upstream Relationship**: Modified Upstream & Newly Created Engine
- **Date**: 2026-08-18

---

## 1. Original Behavior
Upstream risk scoring queried `inherent.risk.level` fixture records stored in PostgreSQL. If any row in the matrix XML data was modified or absent, risk computation failed with foreign key errors.

## 2. Problem / Reason
1. Hidden calculation logic made it difficult for students to explain during viva.
2. Inability to verify calculation independently without database queries.
3. Lack of strict boundary validation for Likelihood and Impact scores.

## 3. Planned Change
Implement a transparent, deterministic qualitative risk scoring engine:
$$\text{Risk Score} = \text{Likelihood} \times \text{Impact}$$
- **Likelihood**: $1$ (Low), $2$ (Medium), $3$ (High).
- **Impact**: $1$ (Low), $2$ (Medium), $3$ (High).
- **Risk Score**: Calculated integer between $1$ and $9$.
- **Risk Level**:
  - **Low**: Score $1 - 2$ (Color: `#10b981` / Emerald)
  - **Medium**: Score $3 - 4$ (Color: `#f59e0b` / Amber)
  - **High**: Score $6 - 9$ (Color: `#ef4444` / Crimson)
- Score and Level are strictly read-only computed properties calculated by the server engine.

## 4. Implementation Details
- Created `risk_calculator.py` providing `calculate_risk(likelihood, impact) -> (score, level, color)`.
- Validated all 9 matrix coordinates:
  - $(1,1) \rightarrow 1$ (Low), $(1,2) \rightarrow 2$ (Low), $(1,3) \rightarrow 3$ (Medium)
  - $(2,1) \rightarrow 2$ (Low), $(2,2) \rightarrow 4$ (Medium), $(2,3) \rightarrow 6$ (High)
  - $(3,1) \rightarrow 3$ (Medium), $(3,2) \rightarrow 6$ (High), $(3,3) \rightarrow 9$ (High)
- Created `risks` table in SQLite with Foreign Key linkage to `assets`.
- Added 4 lifecycle statuses: `Open`, `In Progress`, `Treated`, `Closed`.
